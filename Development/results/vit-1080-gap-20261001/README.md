# ViT 1080 反转：原因 = 900 几何假象 + 1080 attention/QKV 真落后；M32 候选逐位但更慢（2026-10-01）

## 为什么 900 快、1080 慢
- **token 数**：1080 双方都是 640 token，本来就可以直接比；900 我们 400（25×16），他 448。所以 900 那 −38µs 是**形状假象**：按 448 折算（attention 按平方、GEMM 按线性），900 我们已经落后：attention ≈18.4 对 14.8µs，QKV ≈28.4 对 23.3µs。
- **1080 每块逐派发**（我们用 kernel-map-v3 的中位数，单独跑、不含空隙；他用 `pl1-1920x1080.log`，在链里计时、含空隙）：

| 段 | 我们 µs | 他 µs | 差 |
|---|---:|---:|---:|
| attention | 49.7（均值 59.6，含两次约 90µs 的间歇慢派发） | 24.6 | **+25** |
| QKV | 37.0 | 24.8 | **+12** |
| expand | 30.6 | 26.5 | +4 |
| pack | 2.7 | — | +3 |
| contract | 31.8 | 37.1 | −5 |
| project | 11.2 | 11.4 | 0 |

  8 块合计约 +0.31ms，加上 gather 13µs 和间歇慢派发，约 0.4ms。
- **规模效应**：900→1080，他的 attention 只涨到 1.66 倍（448→640），QKV 几乎不变（23.3→24.8，固定开销型）；我们的 attention 随 token 平方涨：一个 wave 管 16 个 query，40 个 key tile 首尾相接串行跑。占用率不是问题（VGPR 68、LDS 0，occupancy 100%）。

## 候选 `HIP_VIT_ATTN_M32`（deep_fast.hip，源码默认 0）
照他 vitattn 一组 32 query：一个 wave 带两条互不相干的 16-query 链，K/V 片段只读一次、两条共用。逐 query 的 WMMA、操作数和 K16 顺序都与生产体相同。宿主不改；网格也不变，多出来的 wave 进来就退。VGPR 68→95，LDS/private 0。宏为 0 重编，代码与现装相同。
- 逐位：**19 组 SAME**（7 用例 × EXACT/AE × 12 帧、AE CSV、900/1080 回绕）。
- ABBA 三轮**全慢**：900 +0.201/+0.213/+0.213ms，1080 +0.145/+0.144/+0.147ms（p99 同样变差，见 `abba-M32.txt`）。不收。
- 原因：wave 数减半（1080 下 1280→640），每个 CU 只剩约 10 个 wave，而每条链是"分数→概率→AV"首尾相接，本来就是延迟链。wave 内交错两条链，补不回 wave 间的并行，K/V 省下的读取也不是瓶颈。和 09-29 "四 wave 一组"的负账方向一致：这个核缺的是并行的独立链，不是复用。

## 结论与下一步
逐位约束下，他的组织方式（一组 32 query、f16 归约）拿不过来：他的 score/分母用 half 累加，不是我们的数学。attention 这 25µs 逐位能动的，只剩在不减 wave 数的前提下加并行：例如把 key 维拆开后再按原 K16 顺序串起来。但分母和 AV 的累加是跨 key 串行的，拆开就改了顺序，**不逐位**。建议下一刀改做 QKV（+12µs/块，他是固定开销型，我们 w5 按 token 线性涨），那是 GEMM，组织改动可以逐位。源码在 `vit-1080-gap` 分支，未并进 main。

## 续：ViT QKV 照他的组织方式重排（`HIP_VIT_QKV_TM`，vit_stream.inc，源码默认 0）
- **他的形状**：`gemmvqkvnorm` 每组 64 token × 256 列，K=1024 一次做完；grid 7×12=84（448 token）/ 10×12=120（640 token），两档都一轮铺满全卡，所以耗时几乎不随 token 数变。我们现役 w5：每 wave 16 token × 1 头（32 列），2 条 K 链各 64 个 WMMA，5 个 wave 共享 LDS 里暂存的权重；1080 是 768 组 × 5 wave。
- **候选**：一个 wave 管 TM 个 16-token tile、同一个头，共 2×TM 条互不依赖的累加链；B 片段读一次，TM 个 tile 共用。逐输出的 K 顺序、片段、范数 tile、行和 WMMA、rsq/scale、byte_F 都与 w5（非 tail-vec）相同。宿主只在模块里有 `_tm4`/`_tm2` 导出时才用，否则仍走 w5。tm4 95 VGPR、tm2 63 VGPR，LDS 4KB，private 0；宏为 0 重编 vit-stream，代码与现装相同。
- **逐位**：TM4、TM2 各 **19 组 SAME**。
- **ABBA 三轮全慢**（`abba-QKV-TM.txt`）：TM4 900 +0.100/+0.112/+0.125，1080 +0.090/+0.084/+0.086ms；TM2 900 +0.105/+0.102/+0.100，1080 +0.122/+0.119/+0.100ms。p99 基本也变差。不收。
- **原因（推断）**：w5 赚在 5 个 wave 共用 LDS 里的一份头权重（每组只读一次）；TM 版每个 wave 从 L2 直接读权重，wave 数又降到 1/TM，WMMA 链虽然更多，但喂数变差。他能靠大块赚，是因为一组 256 列 × 64 token 把 A 和 B 都复用在片上（他是 4 wave 的大工作组）。逐位的话，下一步只能在 w5 的 LDS 暂存上加宽：一组 5 个 wave 各带 2 个 token tile（w5×TM2），或者一组管 2 个头。本轮到此，不继续堆。

## 续二：在 w5 的 LDS 暂存上加宽 + 照他真实形状的大 WG（`HIP_VIT_QKV_WIDE`，源码默认 0）——这条线收尾
同一个模板 `vit_qkv_wide_body<TT,HN,W,CH>`：W 个 wave，每个 wave 带 TT 个 token tile，一组管 HN 个头；头权重按 CH 个 k 步一块，经 LDS 双缓冲暂存（与 w5 同法，只有搬运的分工不同，搬运不涉及舍入）。逐输出的 K 顺序、片段、范数 tile、行和、rsq/scale、byte_F 都与 w5 相同。三版都是 private 0（第一版 st[] 数组被放进 scratch，改成具名寄存器后消除）。

| 候选 | 形状 | VGPR | 逐位 | 900 三轮（ms） | 1080 三轮（ms） |
|---|---|---:|---|---|---|
| WT `w5t2`（bit0） | 5 wave × 2 tile，1 头 | 73 | 19 SAME | +0.168 / +0.156 / +0.167 | +0.160 / +0.156 / +0.159 |
| WH `w5h2`（bit1） | 5 wave × 1 tile，2 头 | 95 | 19 SAME | +0.065 / +0.044 / +0.063 | +0.162 / +0.159 / +0.150 |
| BIG `_big`（bit2） | **他的形状**：4 wave，64 token × 256 列（8 头），CH=2，LDS 32KB，1080 下 grid 120 | 239 | 19 SAME | +0.024 / +0.036 / +0.021 | +0.073 / +0.054 / +0.068 |

p99 同样多数变差（`abba-QKV-wide.txt`）。

**对照实验**：怀疑今天连续的负账是不是宿主问题（base 用 git archive 编，P 用工作树编），于是两个宿主都用与现装相同代码的模块跑了一轮 A/A：900 −0.001、1080 +0.003ms（`abba-AA-control.txt`）。所以测量是干净的，M32/TM/WT/WH/BIG 的负账都是真的。

## 收尾结论（ViT QKV）
- 他的形状可以**逐位**做出来（BIG 19 SAME），但照搬过来仍然比现役 w5 慢：900 约 +0.03ms、1080 约 +0.065ms。它是各版里最接近的，但没有一版赚。
- 推断：他的 QKV 之所以几乎不随 token 变，是一组用 4 个 wave 把 64×256 的输出块整块留在片上。可在我们这里，大块要 239 VGPR，每 SIMD 只能驻留约 1 个 wave，延迟全靠单 wave 内 16 条链去藏，反而不如 w5 的 5 wave × 小块、靠多个 wave 轮流藏延迟。再加上逐位约束，归一化得先把每个头的 32 列写进 LDS 做行和（他在寄存器里用 f16 归约），这一步也拿不过来。
- **这条线收尾**：attention（M32）和 QKV（TM2/TM4/WT/WH/BIG）共 6 个逐位候选都比现役慢，现役 w5 与现役 attention 就是我们在逐位前提下的最优组织。1080 下 ViT 剩下约 0.3ms 的差距，主要来自数值取舍（他在 score、分母、范数上用 half 归约）和他的持久化组织，不在逐位可以重排的范围里。
- 源码都在 `vit-1080-gap` 分支（宏默认 0 + 宿主带回退），没有并进 main，没装机，没发包。

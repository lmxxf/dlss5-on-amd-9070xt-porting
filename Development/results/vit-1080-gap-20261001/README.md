# ViT 1080 反转：原因 = 900 几何假象 + 1080 attention/QKV 真落后；M32 候选逐位但更慢（2026-10-01）

## 为什么 900 快、1080 慢
- **token 数**：1080 双方都是 640 token，本来就可以直接比；900 我们 400（25×16），他 448。所以 900 那 −38µs 是**形状假象**：按 448 折算（attention 按平方、GEMM 按线性），900 我们已经落后：attention ≈18.4 对 14.8µs，QKV ≈28.4 对 23.3µs。
- **1080 每块逐派发**（我们用 kernel-map-v3 的中位数，单独跑、不含空隙；他用 `pl1-1920x1080.log`，在链里计时、含空隙）：

| 段 | 我们 µs | 他 µs | 差 |
|---|---:|---:|---:|
| attention | 49.7（均值 59.6，含两次约 90µs 的间歇慢派发） | 24.6 | **+25** |
| QKV | 37.0 | 24.8 | **+12** |
| expand | 30.6 | 26.5 | +4 |
| pack | 2.7 | — | +3 |
| contract | 31.8 | 37.1 | −5 |
| project | 11.2 | 11.4 | 0 |

  8 块合计约 +0.31ms，加上 gather 13µs 和间歇慢派发，约 0.4ms。
- **规模效应**：900→1080，他的 attention 只涨到 1.66 倍（448→640），QKV 几乎不变（23.3→24.8，固定开销型）；我们的 attention 随 token 平方涨：一个 wave 管 16 个 query，40 个 key tile 首尾相接串行跑。占用率不是问题（VGPR 68、LDS 0，occupancy 100%）。

## 候选 `HIP_VIT_ATTN_M32`（deep_fast.hip，源码默认 0）
照他 vitattn 一组 32 query：一个 wave 带两条互不相干的 16-query 链，K/V 片段只读一次、两条共用。逐 query 的 WMMA、操作数和 K16 顺序都与生产体相同。宿主不改；网格也不变，多出来的 wave 进来就退。VGPR 68→95，LDS/private 0。宏为 0 重编，代码与现装相同。
- 逐位：**19 组 SAME**（7 用例 × EXACT/AE × 12 帧、AE CSV、900/1080 回绕）。
- ABBA 三轮**全慢**：900 +0.201/+0.213/+0.213ms，1080 +0.145/+0.144/+0.147ms（p99 同样变差，见 `abba-M32.txt`）。不收。
- 原因：wave 数减半（1080 下 1280→640），每个 CU 只剩约 10 个 wave，而每条链是"分数→概率→AV"首尾相接，本来就是延迟链。wave 内交错两条链，补不回 wave 间的并行，K/V 省下的读取也不是瓶颈。和 09-29 "四 wave 一组"的负账方向一致：这个核缺的是并行的独立链，不是复用。

## 结论与下一步
逐位约束下，他的组织方式（一组 32 query、f16 归约）拿不过来：他的 score/分母用 half 累加，不是我们的数学。attention 这 25µs 逐位能动的，只剩在不减 wave 数的前提下加并行：例如把 key 维拆开后再按原 K16 顺序串起来。但分母和 AV 的累加是跨 key 串行的，拆开就改了顺序，**不逐位**。建议下一刀改做 QKV（+12µs/块，他是固定开销型，我们 w5 按 token 线性涨），那是 GEMM，组织改动可以逐位。源码在 `vit-1080-gap` 分支，未并进 main。

# C256 链两端进持久化队列（`SP_ENDS`）：逐位且压测通过，但在新基线上 1080 三轮都慢，不收、未装机（2026-10-01）

## 边界上的同类刀：查过了
照 W2_UP_LOW_BYTES 的思路（值本来就在 E4M3 格点上，就改写字节）查 C256 两端：
- 解码链尾块 55：已经由 W2_UP_LOW_BYTES 改成字节（`c256_attn_wave_bo`），没有剩下的活。
- 编码链尾块 22：post 3（Hrtz，f16 精确，**不在 E4M3 格点上**），这种刀不适用。写 f16 需要改池化和 Up48 的 skip 读取（multihead_fast_padded.hip，归 swin 那条线），本轮没碰。
- 编码链首块 15：输入是池化输出的 f32。改字节同样要动池化，不做。
所以这次改走组织方式：900 下块 15、22 还是分核 PDL，4 个派发（块 22 就是 32.3µs 的 f32 出口 `c256_attn_wave`），把它们并进已经在用的 C256 持久化队列。

## 候选 `SP_ENDS` + `W2_SHARED_PLANES`（swin-persistent 模块宏，源码默认 0；宿主按导出 `sp_ends_capable` 自动选择）
- 编码段 15–22 整条进一次队列（900：832 个任务，原来 16–21 是 624 个）。每个任务按层记录 `SpLayer.pad` 的模式位（bit0 输入 f32，bit1 输出 f32）调用生产 `swin_wave2_body` 的对应实例。这些实例和独立的 c256_wave2 / _bo / _bi 核是同一套实例化，1080 生产上块 15/22 本来就走它们。块 22 写 post 3 的 f32，供 skip 和 Down 读取。ABI 没变，pad 本来就是空字段。
- 四个实例各带一份静态 LDS，叠起来 128KB，超过 64KB 上限。`W2_SHARED_PLANES` 让 C256 各实例共用一对 plane（wave_owned_mh.inc 里一处有宏保护的改动），字节不变。
- 资源：sp_run256_w16 仍是 184 VGPR、private 0。宏为 0 重编，与现装代码相同；final（配方开宏）与实测模块代码相同，两个架构都查过。
- 旧宿主（鬼武者 runtime）传 pad=0，在新模块上行为与现在一样。

## 逐位与压测
- 19 组 SAME（7 用例 × EXACT/AE × 12 帧 + AE CSV + 900/1080 回绕），两次基线各跑一遍，都过。
- 超时注入：让第 0 层（块 15）不发布后继，约 120ms 后超时，GPU 串行恢复，实例随后自禁。同步/异步 × 900/1080，4 组 SAME（`SP_GPU_FALLBACK ... code=1 ... ms=121`）。

p99 在当前基线上 1080 三轮都变差。按收活标准（任一轮均值不能变慢）**不收，不装机**。

推断：收益本来就不大，是"少 4 个派发 + 两端的等待被队列掩住"。基线里 C512 变成一核之后，整帧的功耗和时钟分配变了；1080 下多出来的 208 个窗口任务（块 15/22）又挤在同一个持久化派发里，队列尾部变长了。和 pdl-c512、P 那两次是同一类现象：重叠带来的收益被功耗墙和整帧重排吃回。没有计数器，拆不开。

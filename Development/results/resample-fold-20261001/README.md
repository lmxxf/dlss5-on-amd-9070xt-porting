# 下采样折进相邻核（C64/C128）：逐位一致，但两档三轮全慢，不收（2026-10-01）

**对照**：我们的上采样已经全部融进下一块了（`c64_wave2_up` / `c128_wave2_up` / `c32_wave1_up_b8`）。剩下单独派发的是四个下采样：`mh_pool_project_c32_b8`、`group_c64`（900 下 36µs）、`group_c128`（22µs）、`group_c256`。这次先折省得最多的两处：C64、C128 编码段最后一块。新增导出 `c64_wave2_bi_down` / `c128_wave2_bi_down`，宏 `W2_DOWN_FUSED`，源码默认 0。做法是给每个窗口加一段尾处理：先过 workgroup fence，再重读本窗口刚写出的 f32 输出。这里的窗口是 8×8，移位 sx/sy 只取 0 或 4，都是偶数，所以一个窗口正好装下完整的 2×2 池化组，每个池化 token 只由一个窗口计算。每个 lane 直接从 raw 拼出自己那份 A 片段：池化表达式、f16 转换、按 32 列分块的 WMMA 求和、H(acc+sum) 的累加链、最后的 F() 都照搬原池化核，只是换了哪 16 个 token 共用一个 A tile（各行之间互不影响）。宿主只在模块里有 `*_down` 导出时才走融合路径，否则退回原来的 `Down()`，没有运行时开关。

- **资源**：c64_down 143 VGPR / LDS 16KB（原 `c64_wave2_bi` 140 / 8KB）；c128_down 163 / 32KB（原 159 / 16KB）；private 都是 0。尾处理本身不用 LDS。LDS 翻倍是因为编译器给块体本身多分配了一份（和现役 `c64_wave2_bi_bo` 一样是 16KB），不是尾处理带来的。
- **逐位**：基准是现装 31 个模块 + origin/main 宿主。7 个用例 × EXACT/AE × 12 帧，加 AE CSV，加 900/1080 回绕，共 **19 组 SAME**。宏为 0 时重编 c64-wave2，代码与现装相同（compare-modules）。

**结论**：省了 2 次派发和一次 full-res 重读，整帧反而慢 0.05–0.12ms，不收，不装机。原因推断如下（没有计数器，拆不开）：①原池化核是一个独立的宽派发，16 token 一个 tile，满卡并行；折进来以后，它变成每个窗口在块体之后串行跑的尾巴，要多一个屏障、每个 wave 多一段访存延迟链，而且两个 wave 各自重算一遍 A，读 raw 时一条指令打到的缓存行很散（功耗面"触及行数"更多）。②LDS 翻倍，c64 最后一块的占用档变低；这块 900 下本来就要 104µs，被拖慢的时间超过省掉的 36+22µs 池化核和两次约 2.4µs 的派发空隙。mochizuki 能靠融合赚，是因为他整段是一个持久化派发，下采样摊在满载的队列里；我们这里是单窗口核加尾巴，性质不同。C256/C32 用的是同一种尾巴方式，预期也不赚，没有再做。
